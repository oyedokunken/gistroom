- D36 (2026-10-10): ScrollWave moved to the bottom centre of the page on desktop, and phones get a speedometer gauge around the dock chat button. It is not part of the header.
- D37 (2026-10-10): 1:1 calls use plain HS256 LiveKit tokens signed in the web app instead of the LiveKit server SDK, and `livekit-client` is the only new runtime dependency (official client, maintained). Ring timeouts are enforced by client timers, the realtime scheduler and the daily sweep.
- D38 (2026-10-11): The owner wants plain answers on the auth forms instead of identical responses. Sign up says when an email already has an account, forgot password and sign in say when there is no account, and a half finished sign up resumes with a new code. This trades some account privacy for clarity, and every check is rate limited.
- D39 (2026-10-11): The pattern tile placeholder PNGs were deleted. Empty states use the custom icon set. Production storage uses one public bucket for both media and avatars at the owner request, so chat files rely on signed links and unguessable paths rather than a private bucket (this departed from R15 until D87 resolved it in code).
- D40 (2026-10-11): Seeding has two parts. Reference data (the topics) is idempotent and may run on any schema including production with `npm run db:seed:reference`. The demo world (ten labelled demo people, friends, a chat, rooms, a call and notes) only runs on gistroom_dev and gistroom_test through `npm run db:seed`, so production never holds invented people.
- D42 (2026-10-12): Edit and delete for everyone both last 15 minutes (D4 changed from 60). The server enforces the window, the UI only hides the actions.
- D43 (2026-10-12): Room chat is deleted when a room ends. The 24 hour keep time for reports is gone because a report stores its own evidence snapshot when it is made.
- D44 (2026-10-12): Invite link tokens are stored next to their hash so active links can be shown in full to the people who may share them. The hash is still what a link is looked up by.
- D45 (2026-10-12): Activity (what you did) is a Notification of type ACTIVITY that is created already read, expires after 7 days and never goes to push or email.
- D46 (2026-10-12): QA accounts are marked `isInternal` and are hidden from everyone else. `npm run seed:qa` refuses any schema other than gistroom_dev and gistroom_test unless `--allow-prod-qa` is passed, and needs `QA_PASSWORD`.
- D47 (2026-10-12): The demo seed creates no live rooms. Live rooms and their counts come from real LiveKit sessions only. Demo images and voice notes have no stored file, so they show their placeholders.
- D48 (2026-10-13): Sessions last 30 days sliding with a 90 day cap, and the cookie is renewed by the proxy on page loads. The earlier cookie was set once at sign in and never renewed, so it ended 30 days after sign in even for daily users.
- D49 (2026-10-13): The realtime socket never decides a person is signed out. It confirms with `/api/auth/session` and retries on any other failure, because an offline phone or a sleeping server used to send people to the sign in page.
- D50 (2026-10-13): Push subscriptions belong to a device (the `gr_device` cookie, one year), not a session. After a session ends alerts continue for 30 days as plain text, then the device is marked as needing a sign in. Signing out on purpose removes that device's alerts.
- D51 (2026-10-13): Sensitive actions need a sign in from the last 15 minutes. Accounts with a password type it again, Google only accounts sign in again.
- D52 (2026-10-13): Test people are marked `User.isSeed` and only that mark is used to remove them. Their emails are on gmail.com and yahoo.com at the owner request, so they are never emailed: the mail code skips them, and they have no password. They are removed before launch.
- D53 (2026-10-13): Unknown accounts are told at step one of sign in (back to D38), because a person should not type a password into nothing.
- D54 (2026-10-13): Calls are recorded in the chat as system messages that never count as unread.
- D41 (2026-10-11): Notes are private to their author and attach to one chat or one room. Anyone who took part in a room keeps their notes after it ends, and a note is never visible to the other people in the chat or room.
- D55 (2026-10-13): Username and email are permanent. A person who needs a different one makes a new account. This removes two flows that were hard to keep safe.
- D56 (2026-10-13): The data export is a PDF. It is written by `server/account/pdf.ts` with the standard Helvetica fonts instead of a library, because the PDF libraries on npm are either unmaintained (pdf-lib, last release 2022) or heavy (R24). Marks and symbols Helvetica cannot draw are simplified, so a Yoruba name reads without its tone marks. Downloading the report adds a SYSTEM notice so the person sees it happened.
- D57 (2026-10-13): People who want to come to a scheduled public room are added to its member list as INVITED ("Remind me"). Starting the room sends each of them one ROOM_STARTING notice with `live: true`. Private rooms only notify people already invited.
- D58 (2026-10-13): Deleted room chat messages stay as a marker (text cleared, who deleted it kept) until the room ends, so the person who deleted it reads "You deleted a message". Room chat messages can be edited by their sender for 15 minutes, like chat messages. Call reactions travel over the LiveKit data channel and are never stored.
- D59 (2026-10-13): The PDF report embeds the logo as a small JPEG kept in `server/account/pdf-assets.ts` and the person's picture when it is a JPEG (other formats are converted with sharp when the server has it, otherwise initials are drawn). JPEG data goes into the PDF as it is, so the report still needs no PDF library.
- D60 (2026-10-13): Day to day work uses `npm run verify:changed`. The full `npm run verify` is for CI and releases. Section 0 rule 3 of CLAUDE.md is read as: green `verify:changed` while working, green full `verify` before a release.
- D61 (2026-10-13): A "{name} tried to call you" chip has no Call back button, because chips never carry actions (R4 exception). The missed call is in the call log and the notification list, both with a call back button.
- D62 (2026-10-13): The room screen asks "Leave this room?" when you press its own Leave button, and the browser asks before the tab closes or reloads. Moving to another page in the app does not leave the room: the live session stays and an in call bar follows you. The browser Back button is treated as moving to another page.
- D63 (2026-10-13): The caller sees "Calling..." until the call is answered or ends. There is no "Ringing..." step because we have no delivery receipt from the other person's device.
- D64 (2026-10-13): The "You're muted" hint while you speak is not built. It needs a second microphone stream, which could trigger a second permission prompt.
- D65 (2026-10-13): Voice notes, photos and files chosen offline wait in memory and send when the line returns. They are not kept across a reload.
- D66 (2026-10-13): LiveKit webhooks are hints. Each only asks for a reconcile of that room, which reads who is really connected, so repeated and out of order deliveries are harmless.
- D67 (2026-10-13): LiveKit tokens last 9 hours for rooms and 6 hours for calls, so a reconnect late in a long session still works.
- D68 (2026-10-13): Sound settings and the join and leave notice setting live on the device in local storage. Quiet hours come from the notification settings.
- D69 (2026-10-13): Joining a room that has ended shows the ended page itself (with the summary for people who were in it) and not a dialog on top of it.

- D70 (2026-10-14): Registering for a room is `RoomMember.registeredAt` on an INVITED row, not a new table, because the pair is already unique there. People who were invited but never registered get no reminders, only people who put their name down (and the host).
- D71 (2026-10-14): The 15 minute reminder keeps the existing ROOM_STARTING type (settings label "Room reminders") and "live now" is a new ROOM_LIVE_NOW type ("Room is live"). Moved, cancelled and due notices follow the Room reminders switch (`prefKey`). The registration confirmation is an ACTIVITY line (kind room-registered), not its own type.
- D72 (2026-10-14): The reminder windows are read from the rooms, not from the jobs. Jobs (three nudges before, two at the time, two after the grace) only wake the web sweep through the realtime scheduler, and the daily cron is the last net. A reminder more than `ROOM_REMINDER_LATE_MIN` (10) late is dropped, because "live now" or nothing is better than a stale ring.
- D73 (2026-10-14): Quiet hours and Do Not Disturb hold back push for room notices. The in app list and room emails still arrive, since an email is read when the person chooses.
- D74 (2026-10-14): The host's reminder email shows the host's name but not their picture. Email clients block most remote images and Graphik cannot load there, so the plain name is the reliable part.
- D75 (2026-10-14): Moving a scheduled room is an API call (`scheduledFor` in the settings call, host only). There is no date picker for it in the room screen yet.
- D76 (2026-10-14): The call and room window hosts the existing `CallScreen` and `RoomScreen` as they are. The window body is a transformed box, so their fixed full screen layout fills the window and neither screen was rewritten. Inside it the room title is an h2 so the page keeps one h1.
- D77 (2026-10-14): Full screen asks the browser to put the whole document full screen, not only the window, because dialogs are rendered in the page body and would be hidden behind a full screen element.
- D78 (2026-10-14): A phone minimizes a video call to a bubble by scaling the same screen down, so it needs no second layout. The minimized timer on the bar only shows once the connection has started.
- D79 (2026-10-14): Pop out to Document Picture-in-Picture is not built. Moving a live call and room screen into another document needs its styles, fonts and media elements to follow, and we have no device to check it on.
- D80 (2026-10-14): The in call bar is gone. Its job (timer, mute, return, hang up) is the minimized window.
- D81 (2026-10-14): The ring list is worked out by the server and the tab only draws it. Socket events are hints that ask for the list, so a reload, a second tab, a sleeping realtime service and a missed event all end at the same card. Calls reuse the `call:*` events, and room rings use `room:ring` and `ring:*`.
- D82 (2026-10-14): Someone already in a call or room gets a chip with no button, not the "quiet chip with action" the brief describes, because chips never carry actions (R4). The action is in the notification list and the call log, which both have Call back and Join.
- D83 (2026-10-14): "Don't ring me for this room" is on the card as a text button under the three main buttons, and Decline on a room ring is the same as Not now.
- D84 (2026-10-14): A phone ring is a heads-up card. Tapping the name opens a full-screen answer screen with the same buttons. There is no separate swipe or lock screen layout.
- D85 (2026-10-14): The browser tests have no realtime service, so the ring window is proven through the list the server returns. Socket speed, a closed tab ringing by push and the vibration pattern need a real phone and are listed in the report.
- D86 (2026-10-18): R13 is reconciled with what ships. Still art is PNG. The few animated pieces (scenes, maker portraits, form status icons) are animated WebP with alpha next to a PNG still, because PNG cannot animate and the animated budget is 400 KB. Small tool logos on the About page are SVG files. All of it is drawn in code by `scripts/graphics`, not generated, and stays DRAFT in `design/assets.manifest.json` until the owner approves it.
- D87 (2026-10-19): D39 is resolved in code. Chat media is signed and opened only while its bucket is private, exists and is not the avatar bucket, otherwise the person gets a plain error and the log an error. The old public bucket case is closed by `npm run storage:migrate-media` and `npm run storage:check`. Until the owner moves production media, uploads and opening chat media fail closed.
- D88 (2026-10-19): The same origin check runs inside `api()` for every POST, PUT, PATCH and DELETE. Only the LiveKit webhook and the sweep opt out with `csrf: "none"`, because servers call them and each checks its own credential. A test lists every route and fails for a new unprotected one.
- D89 (2026-10-19): Passwords use scrypt N=2^17, r=8, p=1 (OWASP). Old hashes verify and are rewritten after a good sign in, and an old hash that fails a sign in also spends a dummy verification so timing does not tell accounts apart.
- D90 (2026-10-19): Coverage is measured with v8 over unit, integration and socket tests together, with floors set just under the measured numbers in `vitest.config.ts`. Browser specs are not instrumented.
- D91 (2026-10-19): Forwarded client address headers are trusted only on Vercel or with `TRUST_PROXY=true`. Elsewhere all callers share one rate limit key, because route handlers cannot see the socket address.
- D92 (2026-10-20): Production chat media moved to a private bucket named `media` in the same Supabase project. Seven chat files were copied from the old public bucket and their FileAsset rows repointed, and `SUPABASE_MEDIA_BUCKET` is `media` on Vercel production. Avatars stay in the old public bucket. The public copies of the chat files were deliberately left in place, so they are still reachable by their unguessable paths until `--delete-source` is run.
- D93 (2026-11-03): The primary address is `https://gistroom.oyedokun.dev`. It is the canonical URL, the README and docs link to it, `gistroom.vercel.app` redirects pages to it, and it is the first entry in `ALLOWED_ORIGINS`. `gistroom.ng` is left as is for now and stays in the allow list. Email addresses stay on `@gistroom.ng` until a mailbox exists on the new host. Calendar UIDs keep `@gistroom.ng` so existing calendar entries still update.
- D94 (2026-11-09): Forwarding creates a new message from the forwarder and carries only a "Forwarded" flag and the source type. The original sender and time are never carried over, a forward of a forward reads the same (no chain), and only text, photos, videos, voice notes and files can be forwarded. Files are copied to a new path in the destination chat, so deleting the original or its owner's account cannot break the copy and media access is checked against the destination chat. Up to 10 messages to up to 5 friends per request, retries are idempotent through a client generated batch id.
- D95 (2026-11-09): One time notifications keep their dedupe key when read and are tombstoned by their CREATED delivery record when deleted, so a later sweep never repeats them. Only aggregated rows (DM_MESSAGE, ROOM_REGISTRATIONS) release the key on read. Delivery records hold reasons and status codes only and are kept 30 days. A failed scheduled job is retried with a growing wait and dropped after five attempts.
- D100 (2026-11-10): Screen sharing handoff. One person presents at a time. A second person who asks is told who is presenting and offered "Ask to present". The presenter gets a modal and chooses Allow or Not now, and the request lapses after 30 seconds (`PRESENT_REQUEST_TTL_SEC`). Allowing opens a 30 second handoff in which only the asker may start, so nobody can slip in between. In a room the host and moderators may also "Take over", which stops the current presentation by force and is logged. Nothing ever replaces a presenter silently. In a 1:1 call there is no force: either person stops only their own, and the other person can hide the tile on their own screen.
- D101 (2026-11-10): At most one presenter per call or room (`PRESENT_MAX_PRESENTERS`). It is enforced in Postgres (`presenterId` on Call and Room, claimed with a conditional update) and in LiveKit: the screen share source is never in a normal token. The server grants it to the presenter through UpdateParticipant and takes it away when they stop, are removed, banned, handed over or the session ends, and LiveKit then drops the track. The browser track is still the source of truth for what viewers see, and a socket event is only a hint.
- D102 (2026-11-10): Quality and data saver. Sharing captures at most 1080p and 15 frames a second, and screen audio is never shared. With data saver on, "Present now" first explains the cost and asks the person to choose the reduced quality (at most 540p and 5 frames a second) before the browser picker opens. A person on a weak line gets the same cap. The share is published at a single layer, no simulcast, and viewers receive it through adaptive streaming only while the tile is on screen.
- D103 (2026-11-10): No silent fallback. An unsupported browser (most phone browsers), a denied picker, a source the browser ended or a failed publish always shows an inline reason with the next step. It never turns on the camera or falls back to audio, and it never keeps a half started share. Browsers report a closed picker and a blocked permission the same way, so both get one message that covers both (choose a source, or allow it in the site settings). Only a picker that reports an explicit cancel stays silent. A locked room does not stop people already inside from presenting, because a lock only decides who may enter.
- D104 (2026-11-10): Forced stop. In a room the host and moderators can stop a presentation (a new `PRESENT_STOP` action in `RoomModLog`, shown in the moderator log and never carrying a source name). The server revokes the screen share permission, LiveKit drops the track and everyone is told through a hint. Lifecycle outcomes (started, stopped, denied, failed) are logged by pino with ids only. The shared window title, the source name and the pixels are never stored, logged, notified or sent in any event.
- D105 (2026-11-11): Inactive means both signals are older than seven days (`LIMITS.REENGAGE_INACTIVE_DAYS`): no meaningful action (`User.lastActiveAt`) and no session seen (the latest `Session.lastSeenAt` or the socket `User.lastSeenAt`). A person who only holds an old session counts as inactive, and an account younger than seven days never does (its creation date stands in for a missing signal). The spell is keyed by the UTC day of the last signal, so coming back and going quiet again starts a new spell. The pure policy is `decideReengage` in `packages/shared/src/reengage.ts`.
- D106 (2026-11-11): At most one come back notice per 30 days (`REENGAGE_COOLDOWN_DAYS`) and three in any 365 days (`REENGAGE_MAX_PER_YEAR`). `ReengagementNotice` holds one row per person, spell and channel (unique on `userId, windowStart, channel`). The email is claimed with a PENDING row and an attempt counter before it is sent, so overlapping sweeps cannot both send, and it is given up after three failed sends. A crash between the send and the record can send once more, which is accepted. Cooldown, cap, a switched off email and a recipient outside `MAIL_ALLOWED_DOMAINS` write a final SKIPPED row, so the same person is not looked at again for 30 days.
- D107 (2026-11-11): The nudge is a new notification type `REENGAGE` so it has its own switch in Settings. It is in the app and by email, never pushed, and email is on by default. The in app notice is created with a per spell dedupe key whether or not the email is allowed, so it is waiting when the person returns. The copy states no counts, names or rooms. Seed, internal, suspended, deleted and unverified accounts and people who have not finished onboarding are never selected. Quiet hours hold the email (nothing is recorded, a later run tries again) and the in app list is unaffected.
- D108 (2026-11-11): The nudge runs inside the existing sweep, only between 08:00 and 19:59 UTC (09:00 to 20:59 in Lagos) so it never lands at night, and looks at no more than 200 people (`REENGAGE_BATCH`) per run in id order, in pages of 100. Because the daily cron runs at 03:00 UTC, it is the realtime scheduler sweep and the uptime pinger that reach the daytime window. A run that is cut off is safe to repeat.
- D109 (2026-11-11): Notification search runs in Postgres on the person own rows only (`userId` is the first condition, never inside an OR). It matches the text, case insensitive, against a whitelist of payload keys (`SEARCHABLE_PAYLOAD_KEYS`) and against the notification types whose human label or alias contains the text (`notificationSearchAliases`). It is 2 to 60 characters after normalizing, pages by the same (createdAt, id) cursor as the list with no offset, and is backed by an index on `(userId, createdAt desc, id desc)`. The room registration row lists names in an array and is not searched by name. The search text lives in the address as `?q=`.
- D96 (2026-11-09): Badges. Ten families (First room host, Room host, Helpful host, Regular attendee, Conversation starter, Good listener, Community builder, Topic explorer, Consistent gist, Trusted reporter) defined once in `packages/shared/src/badges.ts` with a versioned evaluator. Counts come only from server facts: a hosted room counts when it went live, ended and had at least two people in it, one count per distinct room. A family repeats in fixed steps (5 rooms, 10 friends, 5 topics and so on) and shows as x2, x5. Earned records are permanent: a grant is one row with a unique (person, badge, ordinal) key, is never deleted, and moderation revokes it with a time, an actor and an audit entry, after which the same ordinal is never granted again. Helpful host stops earning while a report against the host or their rooms is open. Friends and activity badges count seeded accounts but never internal accounts. Good listener is kept and means staying 10 minutes or more in a room without being removed. Conversation starter needs at least 3 messages in a chat, or 10 minutes in a room. Trusted reporter is private: only its owner sees it. A person can hide badges from every public surface with "Show badges next to my name", and keeps the record. The summary shown next to a name is kept on the user row so no surface needs an extra query. Badge counts are the active grants, so a revoked grant lowers the count.
- D97 (2026-11-09): Suggested friends use three explainable signals with visible weights: interests in common (3 each), mutual friends (4 each, capped at 10) and public rooms attended together (2 each, capped at 5). Location and language are not used, because nobody has consented to share either and there is no field for it, so nothing coarse or inferred can leak. Private rooms are never read. The list is capped at 12, ordered the same way every time (score, then id), leaves out blocked, deleted, suspended, hidden, unfinished, internal, already connected, pending and cooldown people, and has a Not interested button that is permanent and safe to repeat. The reasons shown are only facts the person already shows or that are public.
- D98 (2026-11-09): Activity is recorded as a time only. `User.lastActiveAt` moves at most once an hour and one `ActivityDay` row is written per Lagos calendar day, when a person sends a message, joins a room, makes a call or answers or sends a friend request. It feeds the come back email and the Consistent gist badge and nothing else.
- D99 (2026-11-09): The public profile adds the date joined (month and year), the number of friends who are still active, interests, whether the email is verified (never the address) and badges. A visitor sees the same fields whether or not they are friends, except friends since. Email and username are permanent: the settings page shows them without any control, and the profile route refuses any request that names either one with a 400, so a crafted request or a stale form cannot change them. An account that never confirmed its email can confirm it from Settings with the same 6 digit code rules as sign up (purpose `VERIFY_EMAIL`, always sent to the address the account already has).
- D110 (2026-11-09): Dependabot ignores major bumps of typescript, eslint and zod. typescript-eslint caps its TypeScript peer at below 6.1, so a TypeScript 7 bump fails `npm install` on Vercel with ERESOLVE. Zod 4 is a breaking migration for the whole repo (it also clears an open high severity audit advisory) and is done as its own slice. Bump these by hand when the tools around them support the new major.
